[지난 글](/dice-dungeon-development)에서는 주사위 두 개로 시작한 게임의 화면과 성장 규칙을 다듬었다. 그때까지는 혼자 플레이해 보고 불편한 곳을 고치면 됐다. 규칙을 바꾸면 다음 판부터 새 규칙으로 하면 그만이었다.

그 뒤로 순위표와 계정 업적을 붙였다. 쉬움부터 지옥까지 난이도마다 적은 턴으로 완주한 기록을 보여 주는 순위표다. 기록이 다른 사람과 비교되기 시작하자 질문이 달라졌다. 이 기록은 정말 이 규칙으로 얻은 것인가. 어제 시작한 모험은 오늘 바뀐 규칙으로 판정해도 되는가. 난이도를 바꿨다면 그 난이도는 여전히 의도한 만큼 어려운가.

> *"규칙을 하나 고쳤을 뿐인데, 어제 세운 기록은 이제 무엇과 비교되는 거지?"*

1편을 쓴 뒤 커밋은 67개가 더 쌓였다. 3막 확장, 난이도별 2~5막 캠페인, 업적 143종 같은 기능도 늘었지만 이번 글에서는 순위표를 믿을 수 있게 만든 과정만 다룬다. 서버가 기록을 다시 계산하게 한 일, 규칙 버전을 나눈 일, 완주율을 측정으로 맞춘 일, 그리고 운영 DB에서 만난 사고다. 같은 기간에 스타일 파일을 화면별로 나눈 정리도 있었지만 이번 글에서는 빼기로 했다.

## 점수는 서버가 다시 계산했다

### 클라이언트가 보낸 승패는 믿지 않기로 했다

브라우저 게임에서 결과를 서버로 보내는 가장 쉬운 방법은 "몇 턴에 이겼다"를 그대로 보내는 것이다. 하지만 그 값은 개발자 도구에서 얼마든지 바꿀 수 있다. 그래서 결과 대신 **결과를 만든 과정을 보내고, 서버가 그 과정을 다시 돌리게** 했다.

게임 판정에 쓰는 난수는 시드에서 만든다. 모험이 시작되면 시드와 난수 상태, 난이도, 규칙 버전을 저장하고, 그 뒤 경로 선택·장비 장착·주사위 배치·재굴림·턴 확정 같은 행동을 전부 로그로 남긴다. 같은 시드에 같은 행동을 넣으면 같은 결과가 나와야 하므로, 서버는 로그를 받아 처음부터 다시 재현한다. 저장하는 값은 재현으로 얻은 턴 수와 남은 생명력이고, 클라이언트가 보낸 점수나 승패는 근거로 쓰지 않는다.

시작 조건도 서버가 정한다. 로그인한 뒤 모험을 시작하면 서버가 계정·난이도·규칙 버전·시드·모험 ID와 7일 만료 시각을 묶어 서명해 준다. 이 서명이 없으면 등록할 수 없으므로, 로그인 없이 하던 모험을 나중에 공식 기록으로 올리는 길도 없앴다. DB에는 검증한 요약 결과와 로그의 SHA-256만 남기고, 전체 로그는 검증에만 쓰고 보관하지 않았다.

이 방식이 막지 못하는 것도 있다. 자동 플레이 프로그램이 만든 로그나 시드를 분석해 만든 로그도 규칙상 유효하면 통과한다. **재현 검증은 규칙을 지켰다는 증명이지, 사람이 직접 했다는 증명은 아니다.** 이 한계는 문서에 그대로 적어 두고, 로그 크기를 1 MiB·행동 12,000개로 제한하는 데서 멈췄다.

### 사망한 기록에도 등록 창이 떴다

검증을 붙인 뒤에도 빈틈이 하나 있었다. 모험이 끝나면 승패와 관계없이 등록 동의 화면이 떴다. 순위표는 완주 기록을 겨루는 곳인데, 최종 보스에게 진 기록도 등록 버튼을 누를 수 있었다.

화면에서 버튼만 숨기는 것으로는 부족했다. 요청은 화면을 거치지 않고도 보낼 수 있기 때문이다. 그래서 서버의 재현 결과에도 완주 조건을 걸었다.

```ts
if (
  state.phase !== 'won' ||
  state.chapter !== rankingRule(start.rules)?.chapters ||
  state.depth !== chapterLength(state) - 1 ||
  state.hp <= 0 ||
  state.enemyHp !== 0
)
  fail('최종 보스를 쓰러뜨리고 모험을 완주한 기록만 랭킹에 등록할 수 있습니다.');
```

순위표 조회에도 마지막 막과 생명력 조건을 넣고, 사망 기록을 승리로 꾸민 제출을 거부하는 테스트를 더했다. 이렇게 하고 나니 테스트에 고정해 둔 쉬움 시드 8이 새 밸런스에서 패배한다는 것도 드러났다. 랭킹 테스트가 그동안 진 모험으로 등록을 검사하고 있었던 셈이라, 이기는 시드로 바꿨다.

### 공개 순위표에는 계정 이름을 싣지 않았다

처음에는 순위표에 로그인 계정의 표시 이름을 보여 줬다. 그런데 Google 계정의 표시 이름은 대개 실명이다. 게임 순위표에 실명이 올라가는 것은 내가 원한 모습이 아니었다.

그래서 등록할 때 캐릭터에 붙인 이름을 저장하고, 이름을 비워 두면 '이름 없는 기사' 같은 직업 기본 이름을 쓰게 했다. 같은 이름을 구분할 수 있도록 이름 아래에 로그인 방식 아이콘과 앞 두 글자만 남긴 이메일(`ab***@gmail.com`)을 붙였다. 전체 이메일과 계정 실명은 공개 응답에 넣지 않는다.

## 규칙을 고칠 때마다 과거가 바뀌었다

### 유물 하나를 고치면 예전 모험의 결과가 달라졌다

재현 검증에는 대가가 있었다. 서버는 로그를 **지금의 코드**로 다시 돌린다. 그러니 규칙을 고치면 고치기 전에 시작한 모험은 다시 돌렸을 때 다른 결과가 나온다.

처음 이 문제가 드러난 건 전설·고유 유물의 중복 획득을 막을 때였다. 같은 유물이 두 번 나오지 않게 추첨을 바꾸면, 이미 진행 중인 모험에 저장된 보상과 재현한 보상이 어긋난다. 저장과 재현이 다르면 그 모험은 검증에 실패한다. 플레이어 입장에서는 아무 잘못 없이 진행하던 모험이 등록할 수 없는 기록이 되는 것이다.

그래서 새 규칙에 번호를 붙였다. 새로 시작한 모험에는 `relicRulesVersion: 1`을 저장하고, 이 값이 없는 저장과 로그는 예전 추첨을 그대로 쓴다. 새 모험의 서명에도 이 번호를 넣어, 등록할 때 번호를 지우거나 바꾸면 거부하게 했다.

```ts
// 버전이 없는 기존 모험은 중복 제한 없이 예전처럼 추첨한다
const heldSingles = (s: GameState) =>
  s.relicRulesVersion === 1 ? s.relics.filter((id) => isSingleCopy(RELIC_BY_ID[id])) : [];
```

### 규칙 번호는 결국 13개가 됐다

한 번 이렇게 하고 나니 규칙을 바꿀 때마다 같은 질문을 하게 됐다. 이 변경이 진행 중인 모험의 판정을 바꾸는가. 바꾼다면 번호를 하나 더 만든다. 지금 게임 상태에는 이런 번호가 13개 있다.

| 번호 | 바뀐 것 |
|---|---|
| `relicRulesVersion` | 전설·고유 유물 중복 획득 제한 |
| `controlRulesVersion` | 방어를 골라도 남은 피해가 있으면 상태 이상 판정 |
| `balanceRulesVersion` | 상위 등급 드랍 확률과 적 체력 배율 |
| `mapVersion` | 지도 생성 규칙(현재 7) |
| `classStatsVersion` · `classCombatVersion` | 직업별 시작 능력치와 직업 전투 효과 |

번호를 하나로 합치지 않은 데는 이유가 있다. 하나로 묶으면 지도만 바꿔도 유물·직업·적 규칙까지 함께 바뀐 것으로 다뤄야 한다. 따로 두면 진행 중인 모험은 자기가 시작한 조합 그대로 끝까지 판정받는다. 그 대신 판정 코드 곳곳에 "이 번호면 예전 계산"이라는 분기가 남는다. 나는 코드가 조금 길어지는 쪽을 택했다. 플레이어의 진행이 업데이트 때문에 무효가 되는 것보다는 그편이 나았다.

### 순위표는 MAJOR 버전마다 하나로 정했다

세부 번호와 별개로, 순위표 전체를 묶는 규칙 ID가 있다. 판정이 크게 바뀌면 이 ID를 새로 만들고 이전 순위표는 조회 전용으로 남긴다. 처음에는 배포 버전마다 순위표를 따로 뒀다. 그런데 v3.0.0 다음 v3.0.1에서 고친 것은 화면 배치와 문구뿐이었다. 그런데도 순위표를 새로 열었다면 v3.0.0에서 세운 기록이 홈 화면에서 사라졌을 것이다.

그래서 버전 번호의 의미부터 정했다.

| 단계 | 기준 | 순위표 |
|---|---|---|
| MAJOR | 막 구성·핵심 전투·성장 구조가 바뀜 | 새로 연다 |
| MINOR | 기존 틀 안에서 사건·유물·직업 등을 추가 | 이어 쓴다 |
| PATCH | 오류 수정, 화면·문구, 소규모 밸런스 | 이어 쓴다 |

순위표는 MAJOR마다 하나(`v3`, `v2`, `v1`)이고, 각 순위표가 어떤 내부 규칙 ID들을 포함하는지는 목록 하나로 관리한다. 같은 MAJOR 안에서 밸런스가 바뀌어 재현 결과가 달라지면 새 규칙 ID를 만들어 그 순위표의 목록에 추가한다. 초기 개발 기간에 쓴 내부 ID 네 개는 `v1` 한 묶음으로 고정하고 앞으로 늘리지 않기로 했다.

```ts
{
  id: RULES_VERSION,          // '2026-10-29.monster-actions-1'
  name: 'v3',
  description: '5막 모험 · 난이도별 2·3·4·5막 완주 · 서로 다른 최종 보스',
  chapters: 5,
  storedRules: [RULES_VERSION],
},
```

규칙이 그대로인 배포는 규칙 ID도 그대로 둔다. 그래야 업데이트 전에 시작한 모험도 업데이트 뒤에 등록할 수 있다. v3.0.1은 이 정책으로 낸 첫 배포였다.

## 완주율은 측정해서 맞췄다

### 손대지 않은 난이도가 14%p 떨어져 있었다

난이도마다 목표 완주율을 정해 두었다. 다섯 직업 평균으로 쉬움 80%, 보통 50%, 어려움 30%, 지옥 10%다. 10월 28일에 자동 플레이로 이 목표를 맞춰 두었다. 그런데 다음 날 배포된 규칙으로 다시 재 보니 쉬움 81.3%, 보통 36.7%, 어려움 16.6%, 지옥 3.7%였다(상황별 전략, 직업당 600판). 보통과 어려움이 목표보다 13~14%p 낮았다.

난이도를 직접 고친 적은 없었다. 그 사이에 바뀐 규칙은 여러 개였다. 유물 중복 제한, 각성 기준 20 XP, 사건 등장 가중치, 상태 이상 규칙이 모두 후보였다. 하나씩 추측해 고치는 대신, 위에서 만든 규칙 번호를 이용해 **한 번에 하나씩만 예전 규칙으로 되돌려** 측정했다(보통·어려움, 직업당 400판).

| 되돌린 규칙 | 보통 | 어려움 |
|---|---:|---:|
| 없음(현재) | 36.1% | 16.5% |
| 유물 중복 제한 | 36.1% | — |
| 각성 20 XP | 36.0% | — |
| 사건 가중치 | 37.8% | 14.3% |
| 상태 이상 규칙 | 50.4% | 30.3% |

상태 이상 규칙 하나만 되돌려도 원래 값이 돌아왔다. 방어 칸을 골라도 남은 피해가 있으면 상태 이상 판정을 받도록 바꿨는데, 그 뒤 완주율을 다시 맞추지 않은 것이 원인이었다. 규칙을 고친 것 자체보다, 고친 뒤 측정을 건너뛴 것이 실수였다. 상위 등급 드랍 확률을 낮추고 적 체력 배율을 다시 맞춘 결과는 쉬움 80.6%, 보통 50.2%, 어려움 29.7%, 지옥 10.1%였다(직업당 600판). 이 조정도 `balanceRulesVersion`으로 나눠, 이전에 시작한 모험은 예전 확률과 체력으로 끝나게 했다.

### 같은 실수를 막으려고 검사 명령을 만들었다

원인을 찾고 나니, 이번처럼 측정을 잊는 일이 다시 생길 것이 분명했다. 그래서 규칙을 바꾼 뒤 한 번에 돌릴 수 있는 검사를 만들었다.

```bash
npm run balance:check
# 직업 5개 × 난이도 4개를 병렬로 자동 플레이
# 직업 평균 완주율이 목표(80/50/30/10)에서 ±5%p를 벗어나면 실패
# 잘못된 저장이 한 번이라도 생겨도 실패
```

직업당 200판 기준으로 약 95초가 걸린다. 만들었을 때 규칙은 81.9 / 51.9 / 29.9 / 9.9%로 통과했다. 정밀한 조정용은 아니다. 규칙을 바꾼 커밋 전에 완주율이 크게 흔들리지 않았는지 확인하는 용도다.

v3.0.0을 낼 때는 기준을 더 좁혔다. 직업 평균으로 통과시키지 않고, 직업 5개 × 난이도 4개의 20개 조합을 각각 쉬움·보통·어려움 ±3%p, 지옥 ±1%p 안에 들게 했다. 최종 검증에 31,000판을 썼다. 기사 지옥은 처음 5,000판에서 11.02%가 나왔다. 반올림하면 11%이니 허용 범위 끝에 걸치는 값이었다. 이 값을 그대로 통과시키지 않았다. 계수를 고정한 상태에서 추가 5,000판을 한 번만 더 재기로 미리 정했다. 앞의 표본을 버리지 않고 합산한 결과가 10.71%(10,000판 중 1,071승)였다.

> *"원하는 숫자가 나올 때까지 다시 돌리면, 그건 측정일까?"*

### 전투 없이 보스까지 가는 지도가 있었다

완주율만 보고는 찾을 수 없는 문제도 있었다. 지도에는 일반전, 미확인 구역, 성소·제단 같은 시설이 섞여 있다. 시드 2,000개 × 3막으로 지도를 분석해 보니 5.8%는 미확인 구역과 시설만 타고 전투 없이 야영지까지 갈 수 있었다. 어느 경로든 최소 전투가 0~1회뿐인 지도도 32%였다.

전투가 없는 길은 위험해 보이지만 실제로는 지름길이었다. 턴 수로 순위를 매기는 순위표에서는 이런 지도를 받은 판이 유리하다. 그래서 `mapVersion` 7에서는 길과 시설 배치는 그대로 두었다. 대신 어느 경로에서도 전투 없는 방이 3칸 연속되면 그 가운데 미확인 구역을 일반전으로 바꾼다. 같은 표본에서 전투 없는 경로는 0%, 경로당 최소 전투는 3회가 됐다. 미확인 구역 비율은 37.3%에서 27.8%로 줄었다. 이번에도 진행 중이던 v6 지도의 모험은 기존 지도를 유지했다.

## 운영 DB는 아직 2막에 머물러 있었다

### 3막 기록이 한 건도 없었다

10월 30일, 랭킹 등록이 안 된다는 것을 알았다. 화면에는 "기록 저장 서비스에 연결할 수 없습니다"가 떴다. 일시적인 장애처럼 보이는 문구였다. 코드를 의심하기 전에 운영 DB를 읽기 전용으로 조회했다.

마지막 등록 기록은 10월 28일 오후 5시(KST)였고, 그 뒤로는 하나도 없었다. 그날은 모험을 2막에서 3막으로 늘린 날이었다. 저장된 기록 중 3막 이상은 0건이었다. 원인은 테이블 제약이었다. `dice_results`를 처음 만들 때 막은 1~2, 지도 칸은 0~9, 생명력은 0~44만 허용하도록 검사 조건을 걸어 두었다. 당시 게임에서는 틀릴 수 없는 범위였다. 3막 확장 뒤로는 완주 기록이 전부 이 조건에 걸렸다.

| 제약 | 처음 | 3막 확장 뒤 필요한 범위 |
|---|---|---|
| 막 | 1~2 | 1~5 (v3 지옥은 5막) |
| 지도 칸 | 0~9 | 0~10 (막마다 11칸) |
| 생명력 | 0~44 | 0~999 (성장으로 44 초과) |

게임 코드에서는 막 수와 지도 길이, 성장 상한을 모두 바꿨다. 테스트도 통과했다. 하지만 테스트는 DB 제약까지 보지 않았다. **같은 규칙이 게임 코드와 DB 제약 두 곳에 있었고, 나는 한 곳만 고쳤다.** 제약을 넓히는 SQL을 운영 DB에 적용하자 등록이 바로 됐다.

### 재시도로 풀리지 않는 오류를 장애로 보여 주지 않았다

원인을 찾는 데 시간이 걸린 이유는 오류 문구에도 있었다. 서버는 DB가 거절한 쓰기를 모두 연결 실패로 처리했다. 하지만 제약 위반은 몇 번을 다시 보내도 같은 결과가 나온다. 사용자에게 "연결할 수 없다"고 알리면 잠시 뒤 다시 시도하라는 뜻으로 읽힌다.

```ts
// Postgres 오류 class 23(제약 위반)은 장애가 아니라 스키마와 규칙의 불일치다
const code = String(objectValue(data).code ?? '');
if (!unauthorized && code.startsWith('23')) {
  console.error('Supabase constraint rejected a write', code, objectValue(data).message);
  throw new ApiError(
    500,
    '기록이 저장 조건에 맞지 않아 등록하지 못했습니다. 다시 시도해도 같으니 관리자에게 알려 주세요.',
  );
}
```

제약 위반은 따로 구분해 서버 로그에 어떤 제약인지 남기게 했다. 반면 열이 없다는 오류는 그대로 두었다. 시작 유물이나 외형처럼 나중에 추가한 열이 아직 DB에 없으면 그 값을 빼고 다시 저장하는 대체 경로가 이 오류에 의존하기 때문이다.

### 스키마 원본은 다른 저장소에 있었다

이 테이블의 마이그레이션은 게임 저장소가 아니라 블로그 저장소가 관리한다. 블로그와 게임이 같은 Supabase 프로젝트와 로그인 계정을 공유하기 때문이다. 게임 쪽에서 규칙을 바꿀 때 DB 제약이 눈에 들어오지 않았던 것도 이 구조 때문이었다.

그래서 적용한 SQL을 게임 저장소의 `docs/sql/`에 남기고, 랭킹 문서에 한 줄을 더했다. 막 수·지도 길이·생명력 상한을 바꾸면 DB 제약도 함께 확인한다. 같은 변경은 블로그 저장소에도 마이그레이션으로 추가해, 운영 DB와 스키마 원본이 어긋나지 않게 했다.

## 결과

| 순위표를 열기 전 | 지금 |
|---|---|
| 결과 값을 그대로 저장 | 서버가 시드와 행동 로그로 재현한 값만 저장 |
| 진 모험도 등록 화면이 뜸 | 화면과 서버 모두 완주 기록만 받음 |
| 규칙을 고치면 진행 중인 모험이 무효가 될 수 있음 | 규칙 번호 13개로 시작한 조합을 끝까지 유지 |
| 배포 버전마다 순위표 | MAJOR 버전마다 순위표, PATCH·MINOR는 이어 씀 |
| 완주율을 기억에 의존해 다시 맞춤 | `balance:check`가 목표 ±5%p를 벗어나면 실패 |
| 전투 없이 보스까지 가는 지도 5.8% | 모든 경로 최소 3전투 |
| DB 거절이 "연결할 수 없음"으로 보임 | 제약 위반을 구분해 알리고 로그에 남김 |
| 계정 표시 이름(실명일 수 있음)을 공개 | 캐릭터 이름과 가린 이메일로 구분 |

마지막으로 확인한 상태에서 전체 테스트 432개가 통과했다. 여기에는 등록할 때의 리플레이 검증, 이전 규칙 서명 거절, 순위 계산 테스트가 들어 있다. 운영 사이트의 순위표 조회 API가 네 난이도 모두 정상 응답하고 기존 기록도 그대로 나오는 것도 확인했다. DB 제약을 고친 직후에는 실제 로그인 계정으로 등록이 되는 것을 확인했다.

확인하지 못한 것도 있다. v3.0.1을 배포한 뒤 로그인 계정으로 새 모험을 처음부터 완주해 등록하는 흐름은 아직 다시 해 보지 않았다. 완주율은 정해 둔 자동 전략과 시드 표본으로 잰 값이라, 사람이 플레이했을 때의 승률을 보장하지 않는다. 자동 플레이로 만든 로그를 걸러 내는 장치도 없다.

## 느낀점

- **순위표를 여는 순간 규칙은 약속이 됐다.** 혼자 할 때는 규칙을 고치면 그만이었다. 기록이 남기 시작하니 고치기 전에 시작한 모험을 어떻게 판정할지부터 정해야 했다.
- **재현 검증은 규칙 번호와 한 세트였다.** 서버가 로그를 다시 돌리는 구조는 믿을 만했지만, 규칙을 바꿀 때마다 과거 기록이 흔들렸다. 번호를 나눠 저장하지 않았다면 업데이트마다 진행 중인 모험을 버려야 했을 것이다.
- **고친 곳보다 측정을 건너뛴 곳에서 문제가 났다.** 완주율 하락도 DB 사고도 코드는 의도대로 동작했다. 바꾼 뒤에 확인해야 할 곳을 확인하지 않은 것이 원인이었다.
- **같은 규칙이 두 곳에 있으면 한 곳은 잊힌다.** 막 수와 생명력 상한은 게임 코드와 DB 제약에 함께 있었다. 이제는 상한을 바꿀 때 확인할 곳을 문서에 적어 둔다.
- **다시 돌릴 수 있다는 것이 원하는 숫자가 나올 때까지 돌려도 된다는 뜻은 아니었다.** 표본을 더 잴 때는 몇 판을 더 잴지 먼저 정하고, 앞의 결과도 버리지 않았다.

처음에는 순위표가 기능 하나라고 생각했다. 붙이고 나니 이 게임에서 가장 많은 규칙을 만들게 한 기능이었다. 규칙을 언제 새로 정하고, 이전 기록을 어디까지 인정하는지가 모두 그 안에 들어 있었다.

다음에는 이렇게 만든 검사 장치들이 실제 업데이트에서 얼마나 문제를 미리 잡는지 지켜볼 생각이다. 여기까지 읽어주신 분들께 감사드리며 이번 글을 마친다.
