[지난 글](/bulmeong-development-2)에서는 숯으로 쉼터를 짓고, 계정에 진행과 기록을 남기는 과정을 정리했다. 다시 돌아왔을 때 이어 할 것이 생겼지만, 돌아오는 방법까지 편해진 것은 아니었다. 휴대폰에서 버튼을 찾고 설치 방법을 알아내는 일, 다른 앱을 보는 동안 소리가 이어지는 일은 각각 따로 맞춰야 했다.

브라우저에서 실행된다는 사실은 시작을 가볍게 해줬다. 링크를 열면 게임에 들어갈 수 있고 별도의 배포 파일을 받지 않아도 됐다. 반면 같은 코드라도 일반 탭과 설치된 앱, 세로 화면과 가로 화면에서 만나는 조건은 달랐다. 게임 안의 상태가 맞아도 그 상태에 접근하는 화면이 불편할 수 있었다.

> *"다시 찾아올 캠프를 만들었는데, 들어오는 길과 내려두는 순간은 괜찮을까?"*

그래서 모바일 조작과 설치 안내, 백그라운드 재생을 함께 살폈다. 업데이트 뒤 다시 받는 파일과 기기에 남는 캐시도 정리했다. 이번 글은 11월 4일부터 6일 사이에 브라우저에서 만난 문제와 그 수정 과정을 중심으로 쓴 기록이다.

## 넓은 화면이라고 PC는 아니었다

### 버튼을 줄이기 전에 묶음을 정했다

나무 베기와 장작 패기, 불 피우기, 이동과 설정이 붙으면서 화면에서 접근할 기능도 늘었다. PC에서는 단축키를 쓸 수 있지만 휴대폰에서는 화면에 있는 버튼을 찾아 눌러야 했다. 버튼을 전부 같은 줄에 놓거나 각각 작은 크기로 줄이는 것만으로 해결하기 어려웠다. 조작부가 장면을 차지하는 정도와 펼친 메뉴가 들어갈 자리를 함께 봐야 했다.

먼저 휴대폰에 맞는 조작 배치를 만들고, 흩어져 있던 보조 조작을 하나의 펼침 메뉴로 모았다. 자주 쓰는 동작은 바깥에서 접근하고, 설정이나 다른 기능은 메뉴 안에서 여는 방식이었다. 새 메뉴를 열면 이미 열려 있던 상자는 닫히도록 했다. 여러 상자가 동시에 떠서 좁은 화면을 덮는 상태를 피하려는 정리였다.

이 규칙은 이후 PC와 모바일의 공통 메뉴에도 이어졌다. 현재 조작부는 나무 캐기부터 장작 넣기와 실내 이동까지 기본 행동을 바깥에 두고, 나머지는 메뉴에서 연다. 다만 지금의 배치 전체가 첫 모바일 수정 때 완성됐던 것은 아니다. 초기에는 폰의 보조 조작을 한곳에 모으는 것부터 시작했다.

### 가로로 돌리자 위쪽이 화면 밖으로 나갔다

세로 화면에 맞춘 뒤에도 가로로 돌린 휴대폰에서 문제가 남았다. 화면 폭이 넓어지면서 PC용 두 열 설정이 적용됐지만 높이는 낮았다. 기존의 짧은 화면용 높이 제한이 다른 규칙에 덮였고, 설정과 쉼터 상자의 윗부분이 화면 밖으로 올라갔다. 폭을 기준으로 구분한 레이아웃이 높이 조건을 놓친 것이다.

당시 수정 기록에는 844×390 화면에서 설정 상자가 화면 위로 133px, 740×360 화면에서 쉼터 상자가 25px 벗어난 값이 남아 있다. 이 수치는 그때 확인한 두 화면의 위치이며 모든 기기의 측정값은 아니다. 폭 720px 이상이면서 높이가 600px 이하인 경우에는 상자의 최대 높이를 다시 제한하고, 넘치는 내용만 안에서 스크롤하도록 바꿨다. 일반적인 넓은 PC 화면에서는 기존 두 열 배치를 유지했다.

| 화면 조건 | 문제가 된 가정 | 바꾼 방식 |
| --- | --- | --- |
| 좁고 세로로 긴 폰 | 버튼을 그대로 줄이면 된다 | 기본 행동과 보조 메뉴를 나눔 |
| 넓고 낮은 가로 폰 | 폭이 넓으면 PC처럼 높이도 충분하다 | 화면 높이로 상자를 제한하고 내부 스크롤 |
| 내용이 많은 설정 상자 | 펼치기만 하면 접근할 수 있다 | 바깥 경계와 안쪽 스크롤을 함께 확인 |

**화면의 폭과 쓸 수 있는 높이는 다른 조건**이었다. 반응형이라는 이름 아래 한쪽만 보고 나누면, 화면 회전처럼 둘이 다르게 움직이는 상황을 놓치기 쉬웠다. 이번에는 메뉴의 위치와 크기를 실제 화면 경계로 확인해야 문제가 드러났다.

### 상자의 동작과 게임의 동작을 나눴다

메뉴가 늘면서 `main.ts`에는 장면 갱신과 계정·설정·쉼터 화면 코드가 함께 들어 있었다. 화면을 고칠 때 게임의 동작까지 한 파일에서 따라가야 했다. 계정과 설정, 쉼터 패널을 나누고 하단 바와 펼침 메뉴의 공통 동작도 별도 모듈로 옮겼다. DOM 요소를 찾는 도구와 한국어 조사 처리도 함께 분리했다.

쉼터 패널을 옮긴다고 쉼터를 짓는 처리까지 모두 옮기지는 않았다. 짓기와 선택은 장면과 저장을 바꾸므로 게임 쪽에 남기고, 패널은 화면을 그리고 선택 결과를 전달하게 했다. 메뉴 모듈은 하나만 열기, 다른 버튼을 누르면 닫기 같은 규칙을 맡았다. 파일을 나누는 기준을 화면의 이름뿐 아니라 **무엇을 바꾸는 코드인지**에 뒀다.

이 변경에서는 새 동작을 추가하기보다 기존 동작을 유지하는 것이 중요했다. 당시 커밋에는 메뉴 버튼과 단축키, 폰의 펼침 메뉴와 계정 통계를 같은 브라우저 흐름으로 비교한 기록이 남아 있다. CSS를 합칠 때도 넓은 화면과 폰의 여러 상태에서 계산된 스타일을 비교했다. 파일이 짧아졌다는 것만으로 정리가 끝났다고 판단하지 않았다.

## 설치 버튼이 설치를 보장하지는 않았다

### 설치할 수 있는 상태와 방법 안내를 구분했다

홈 화면에서 바로 열 수 있도록 웹 앱 설치 기능을 붙였다. 매니페스트와 아이콘을 두고, 브라우저가 설치 요청을 제공하면 그 요청을 보관했다가 버튼을 누를 때 사용했다. 이 경로에서는 사용자가 게임 안의 안내에서 실제 설치 창으로 이어질 수 있었다. 하지만 모든 방문이 같은 설치 요청을 주는 것은 아니었다.

메신저 안에서 링크를 열거나, 직접 설치 창을 제공하지 않는 환경에서는 다른 안내가 필요했다. 설치 요청이 없는데 같은 버튼만 보여주면 눌러도 기대한 창으로 이어지지 않는다. 그래서 요청을 받은 경우의 설치와, 받지 못한 경우의 설치 방법 안내를 나눴다. 앱 안 브라우저에서 바깥 브라우저로 여는 안내와 홈 화면에 추가하는 안내도 구분했다.

이것은 브라우저별 설치를 모두 같은 방식으로 강제하는 구현이 아니다. 이 앱이 당시 구분한 환경에 맞춰 다음 행동을 안내하는 방식이었다. 실제 설치 가능 여부와 메뉴 모양은 해당 기기에서 확인해야 한다. 이미 설치된 앱으로 열었을 때는 설치 안내와 버튼을 숨겼다.

### 자동으로 뜬 안내는 계속 남겨두지 않았다

설치 기능을 발견할 수 있게 만드는 것과 안내를 계속 띄워두는 것은 달랐다. 불을 바라보려고 들어왔는데 설치 안내가 화면 아래를 계속 차지하면, 본래 보려던 장면보다 안내가 먼저 보인다. 그래서 자동으로 뜬 안내는 일정 시간이 지나면 사라지도록 했다. 사용자가 손가락이나 마우스를 올리거나 키보드 초점을 둔 동안에는 기다렸다.

직접 메뉴에서 설치를 다시 여는 길은 남겼다. 자동 안내를 놓쳤다는 이유로 기능까지 찾을 수 없게 만들 필요는 없었다. ‘나중에’를 선택하면 한동안 자동으로 다시 띄우지 않게 했고, 설치가 끝나면 관련 표시를 정리했다. 안내의 수명을 기능의 수명과 나눠 다룬 셈이다.

설치했다고 네이티브 앱과 같은 권한을 얻는 것도 아니었다. 저장된 화면을 다시 여는 것, 로그인 요청이 서버에 도달하는 것, 백그라운드에서 소리가 이어지는 것은 별개의 문제였다. 홈 화면에 아이콘이 생겼다는 사실만으로 나머지 동작까지 해결됐다고 보지 않기로 했다.

## 알림 모양을 고치다 재생 경로를 되돌렸다

### 일반 알림과 재생 중인 미디어는 달랐다

불멍은 화면을 계속 보고 있지 않아도 소리를 들을 수 있는 게임이었다. 그런데 한때 폰의 상태 표시를 선택적으로 켜는 일반 알림으로 바꾸면서, 알림을 켜지 않은 경우 화면이 숨자마자 불소리가 멈추게 됐다. 재생 중인 미디어로 남겨두는 경로도 빠졌다. 홈 화면으로 나가면 소리가 끊기고 기본 알림도 보이지 않는 상태였다.

이를 다시 미디어 알림으로 연결했다. 거의 들리지 않는 작은 소리의 파일을 `<audio>`에서 반복 재생하고, 실제 불소리는 기존 Web Audio가 내도록 했다. 알림의 재생·일시정지 버튼은 불소리를 제어하게 연결했다. 시작 버튼을 누르는 사용자 동작 안에서 재생을 요청하고, 재생이 막힌 경우도 따로 처리했다.

여기서 ‘알림을 지원한다’와 ‘재생이 실제로 시작됐다’를 구분했다. API가 존재해도 오디오 재생이 막힐 수 있기 때문이다. 알림을 유지할 수 없는 모바일 환경에서는 화면이 숨었을 때 소리를 멈추는 처리를 남겼다. 이 방식이 모든 기기에서 무조건 소리를 유지한다는 보장은 하지 않았다.

### 진행 막대를 없애려다 알림까지 사라졌다

반복 재생하는 파일은 10초 길이였다. 폰의 미디어 플레이어는 이 길이를 보고 진행 막대를 그렸고, 반복될 때마다 처음으로 돌아가는 모양이 생겼다. 실제로 듣는 것은 시간에 따라 달라지는 불소리인데, 화면은 같은 짧은 곡을 계속 돌리는 것처럼 보일 수 있었다. 이를 실시간 재생처럼 표시하려고 길이를 무한으로 전달했다.

헤드리스 Chromium에서는 그 값을 받아들이고 반복 뒤에도 유지하는 것을 확인했다. 하지만 브라우저가 값을 받았다는 사실과 폰이 그리는 알림 모양은 같지 않았다. 길이 없는 미디어 스트림을 오디오의 출처로 쓰는 실험까지 이어졌다. 설치된 앱에서도 확인할 수 있도록 출처 선택을 기기에 저장하는 방식도 잠시 들어갔다.

결과는 채택하지 않았다. 실제 폰에서 스트림을 쓰자 진행 막대 대신 **미디어 알림 자체가 사라졌다.** 반복 파일로 돌아가고 실험용 선택값도 정리했다. 무한 길이 상태를 전달하는 처리는 남았지만, 그것만으로 기기의 진행 막대가 반드시 사라진다고 설명할 수는 없었다.

> *"브라우저가 값을 받았다는 확인을, 폰 화면이 바뀌었다는 확인으로 대신한 것은 아닐까?"*

| 시도 | 확인한 것 | 최종 판단 |
| --- | --- | --- |
| 반복 파일과 미디어 알림 | 재생·일시정지와 상태 정보를 연결 | 기본 경로로 유지 |
| 무한 길이 위치 정보 | 헤드리스 브라우저가 값을 수용 | 실제 알림 표시까지 보장하지 않음 |
| 길이 없는 미디어 스트림 | 폰에서 미디어 알림이 사라짐 | 실험을 되돌리고 선택값 정리 |

알림 문구도 실제 표시 방식에 맞춰 줄였다. 앱 이름과 상태를 여러 줄로 구분해 전달해도 기기가 한 줄로 합쳐 보여주면 중요한 내용이 밀린다. 당시 확인한 폰에서는 불 상태를 제목으로 두고 날씨와 시각을 이어 표시하는 방향으로 바꿨다. 문구를 어떤 필드에 넣었는지보다 사용자가 실제로 읽는 한 줄을 기준으로 정리했다.

### 터치가 된다는 이유로 폰이라고 보지 않았다

백그라운드 정책을 적용할 기기를 고르는 조건에도 문제가 있었다. 마우스 호버가 없고 포인터가 거칠다는 입력 조건만으로 폰을 분류하면 터치 PC까지 같은 쪽에 들어갈 수 있었다. 그 결과 PC에서 창을 숨겼을 때도 모바일용 중단 정책이 적용될 수 있었다. 입력 장치의 특징을 실행 환경 전체로 확대했던 것이다.

모바일 판단을 별도 함수로 옮기고, 터치 PC와 모바일의 사례를 나눠 검사했다. PC는 알림이 없더라도 기존 소리를 이어가고, 모바일에는 알림 상태에 따른 정책을 적용했다. 이것 역시 모든 기기 구분을 완벽하게 해결했다는 의미는 아니다. 적어도 이미 확인한 터치 PC를 폰으로 잘못 다루는 경로는 명시적으로 분리했다.

## 다시 받을 파일과 남길 파일을 골랐다

### 느려질 때 조절하는 값도 따로 뒀다

이보다 앞선 11월 3일 구현에는 화면을 그리는 해상도를 자동으로 조절하는 처리도 들어 있었다. 일정 시간 모은 프레임 시간이 길어지면 렌더링 배율을 낮추고, 여유가 생기면 다시 올렸다. 탭 전환으로 생긴 긴 공백은 성능 판단에서 제외했다. 화면의 CSS 크기를 줄이는 대신 내부에서 그리는 해상도를 조절하는 방식이었다.

주소에 `?fps`를 붙이면 초당 프레임 수와 가장 느린 프레임 시간, 그리기 횟수와 해상도를 확인할 수 있게 했다. 비교할 때는 `?fixedres`로 자동 조절을 끌 수 있었다. 자동 조절이 켜진 상태에서 프레임 수만 보면 해상도를 낮춘 결과인지 코드가 가벼워진 결과인지 구분하기 어렵다. 이 글에서 새로운 성능 수치를 제시하지는 않지만, 비교할 조건을 고정할 수 있는 장치는 함께 남겨뒀다.

### 라이브러리까지 매번 새로 받지 않게 했다

다시 방문하는 흐름을 만들고 나니 배포 때마다 바뀌는 파일도 눈에 들어왔다. 게임 코드와 Three.js가 한 묶음으로 나가면 게임 코드만 수정해도 전체 파일의 해시가 바뀐다. 브라우저에 이전 파일이 남아 있어도 새 이름의 파일을 다시 받아야 했다. 캐시가 있다는 사실만으로 재방문 비용이 줄어드는 것은 아니었다.

라이브러리를 별도 묶음으로 나눴다. 당시 테스트 빌드에서는 게임 코드만 바꿨을 때 라이브러리 파일의 해시가 유지되는 것을 확인했다. 게임 부분은 새로 받고 바뀌지 않은 라이브러리는 저장된 파일을 쓸 수 있는 구조였다. 이는 해당 빌드에서의 확인이며, 지금의 전체 전송량이나 실제 이용자의 로딩 시간을 측정한 결과로 확대하지 않았다.

페이지와 빌드 파일의 조회 순서도 달리 뒀다. HTML은 네트워크를 먼저 보고 실패하면 저장된 화면을 쓰고, 해시가 붙은 빌드 파일은 저장본을 먼저 확인했다. 계정 API와 다른 도메인 요청은 서비스 워커가 가로채지 않게 했다. 저장된 화면이 열리는 것과 로그인·계정 저장이 오프라인에서 동작하는 것은 별개의 조건이었다.

### 같은 캐시 이름 아래 옛 배포가 쌓였다

빠르게 다시 쓰도록 저장한 파일에는 정리도 필요했다. 캐시 이름은 그대로인데 배포할 때마다 해시가 다른 JS와 CSS가 생겼다. 활성화 시 다른 이름의 캐시를 지우는 코드만으로는 같은 캐시 안에 남은 옛 파일이 사라지지 않았다. 업데이트를 할수록 이전 배포의 자산이 기기에 쌓이는 구조였다.

새 HTML을 받으면 그 페이지가 사용하는 빌드 파일을 찾아 남기고 나머지를 지우도록 바꿨다. HTML에 직접 적힌 파일만 보면 부족했다. JS에서 나중에 불러오는 조각과 CSS가 참조하는 이미지도 연결된 파일이기 때문이다. 이미 저장된 JS와 CSS의 참조를 따라가면서 유지할 목록을 넓혔다.

개발 서버처럼 빌드 자산 참조가 없는 페이지는 정리 근거로 쓰지 않았다. 그 페이지에 해시 파일이 없다는 이유로 기존 캐시를 전부 지우는 것은 다른 행동이다. 실제 서비스 워커 코드를 가짜 캐시 위에서 실행하는 검사에는 새 배포의 자산 보존, 간접 참조 보존, 빌드 자산 없는 페이지의 무삭제가 들어갔다. 저장과 삭제 양쪽의 조건을 함께 확인해야 했다.

## 결과

진행을 저장할 수 있게 만든 다음에는, 그 진행에 다시 접근하는 환경을 손봤다. 모바일 메뉴를 묶고 가로 화면의 높이를 제한했으며, 설치 요청이 없는 환경에는 방법을 안내했다. 백그라운드에서는 미디어 알림과 불소리를 연결했지만, 실제 폰에서 실패한 스트림 방식은 되돌렸다. 재방문할 때 받는 라이브러리와 기기에 남는 이전 배포 파일도 구분했다.

| 문제 | 정리한 방향 |
| --- | --- |
| 작은 화면에 조작과 상자가 흩어짐 | 기본 행동과 펼침 메뉴, 하나만 열리는 상자 |
| 가로 폰의 상자가 화면 위로 벗어남 | 폭뿐 아니라 높이도 제한 |
| 설치 요청이 없는 환경에서 막힘 | 직접 설치와 설치 방법 안내를 분리 |
| 화면을 내리면 불소리가 끊김 | 재생 상태와 미디어 알림을 연결 |
| 알림 표시 실험에서 알림 자체가 사라짐 | 반복 파일로 복구하고 실험 설정 정리 |
| 게임 수정마다 라이브러리도 다시 받음 | 라이브러리 묶음을 별도로 분리 |
| 이전 배포 자산이 계속 남음 | 새 페이지의 직접·간접 참조를 기준으로 정리 |

당시 커밋에는 헤드리스 브라우저의 재생·일시정지 확인, UI 분리 전후 비교, 빌드 해시 비교와 서비스 워커 회귀 검사의 결과가 남아 있다. 이 글은 그 기록과 현재 구현을 대조해 정리했다. 특히 무한 길이를 브라우저가 받아들인 결과와 실제 폰에서 알림이 표시된 결과를 같은 검증으로 취급하지 않았다.

이번 집필에서는 현재 코드의 서비스 워커 캐시와 백그라운드 오디오 정책 자동 검사를 실행해 통과했다. 당시 버전의 폰 설치와 잠금 화면 재생을 직접 다시 확인한 것은 아니다. 설치와 미디어 알림은 현재 기기의 브라우저와 시스템에서 다시 확인할 부분이 남아 있다. 이전 빌드 수치를 현재 로딩 속도로 쓰거나, 저장된 화면이 열린다는 것을 모든 기능의 오프라인 동작으로 설명하지 않았다.

## 느낀점

- **화면의 크기는 폭 하나가 아니었다.** 가로로 돌린 폰은 넓지만 낮았다. 메뉴 배치를 바꾸는 규칙과 화면 안에 남기는 규칙을 함께 확인해야 했다.
- **설치와 재생은 각각의 상태를 확인해야 했다.** 설치 요청을 받을 수 있는지, 오디오 재생이 시작됐는지, 알림을 유지할 수 있는지는 서로 다른 조건이었다.
- **기기가 그리는 화면은 직접 봐야 했다.** 브라우저가 API 값을 받아들여도 시스템 알림이 의도한 모양이 된 것은 아니었다. 실패한 스트림 실험은 되돌리는 쪽을 택했다.
- **캐시를 쓰려면 남길 기준도 필요했다.** 파일을 저장하는 것만으로는 이전 배포가 정리되지 않았다. 지금 페이지가 쓰는 파일과 그 파일이 참조하는 자산을 함께 봤다.

불멍을 다시 열고 다른 앱을 보다가 돌아오는 과정도 게임 경험의 일부였다. 이 경계를 정리하면서 웹으로 만든다는 것이 같은 화면을 여러 크기로 보여주는 일에 그치지 않는다는 것을 확인했다. 할 수 있는 일을 연결하는 것과 환경마다 다르게 남는 한계를 구분하는 일이 함께 필요했다.

같은 시기 화면 안에서는 캐릭터가 장작을 집고 몸을 숙이는 동작도 바뀌고 있었다. [다음 글](/bulmeong-development-4)에서는 브라우저 바깥의 조건에서 다시 장면 안으로 들어가, 그 캐릭터의 동작과 모델을 다듬은 과정을 정리하려 한다. 여기까지 읽어주신 분들께 감사드리며 이번 글을 마친다.
