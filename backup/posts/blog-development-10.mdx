이 블로그에는 조회수와 댓글이 있었다. 글을 읽었다는 숫자는 남고, 하고 싶은 말이 있으면 댓글을 쓸 수 있었다. 그 사이에 가볍게 반응하는 방법은 없었다.

좋아요는 화면에서 보면 작다. 하트 하나와 숫자 하나면 된다. 그런데 그 숫자를 누가 올렸는지, 다시 누르면 어떻게 되는지, 로그인한 사람이 바뀌면 무엇을 보여줄지까지 정해야 했다.

> *"버튼 하나인데, 버튼만 만들면 끝나는 게 아니었다."*

그래서 글과 댓글에 좋아요를 붙이면서 저장부터 화면까지 함께 정리하기로 했다. 본문에만 버튼을 놓는 것으로 끝내지 않고, 목록과 검색 결과와 관리 화면에서도 같은 집계를 볼 수 있게 했다. 이번 글은 그 과정에서 정한 경계들에 대한 기록이다.

---

## 숫자보다 먼저 정한 것

### 누를 수 있는 대상부터 좁혔다

좋아요를 만들면서 먼저 정한 건 색이나 아이콘이 아니었다. **누가 무엇에 반응할 수 있는지**였다. 기존 GitHub 로그인을 그대로 쓰고, 공개된 글과 그 아래 살아 있는 댓글에만 좋아요를 허용했다.

| 상황 | 동작 |
| --- | --- |
| 로그인하지 않은 독자 | 개수는 보고, 누르면 로그인 화면으로 이동 |
| 로그인한 독자 | 다른 사람이 쓴 공개 글·댓글에 등록과 취소 |
| 본인이 쓴 글·댓글 | 개수만 표시 |
| 초안이나 삭제된 댓글 | 좋아요 대상에서 제외 |
| 초안으로 바뀐 글의 댓글 | 댓글이 남아 있어도 좋아요 대상에서 제외 |

댓글만 살아 있다고 충분한 게 아니었다. 그 댓글이 달린 글도 공개 상태여야 했다. 그래서 댓글의 존재와 삭제 여부를 확인한 뒤, 부모 글의 상태까지 확인하도록 했다.

본인 콘텐츠에는 비활성 버튼 대신 집계만 보여줬다. 누를 수 없는 숫자가 버튼 모양으로 남아 있으면 왜 안 눌리는지부터 설명해야 한다. 아예 읽는 요소로 그리는 쪽이 이 블로그의 다른 화면과도 맞았다.

물론 화면에서 버튼을 빼는 것으로 끝내지는 않았다. 서버에서도 작성자를 비교해 본인 콘텐츠에 대한 요청을 거절했다. 초안과 삭제된 댓글도 같은 자리에서 걸렀다.

### 클릭 이력 대신 현재 선택을 남겼다

저장할 것은 모든 클릭의 기록이 아니라 **누가 무엇에 좋아요를 남겨둔 상태인지**였다. `post_likes`와 `comment_likes` 테이블을 따로 만들었다. 글이나 댓글의 ID와 사용자 ID를 묶어 기본 키로 삼았다.

```sql
CREATE TABLE "post_likes" (
    "post_id" TEXT NOT NULL,
    "user_id" UUID NOT NULL,
    CONSTRAINT "post_likes_pkey"
        PRIMARY KEY ("post_id", "user_id"),
    CONSTRAINT "post_likes_post_id_fkey"
        FOREIGN KEY ("post_id") REFERENCES "posts"("id")
        ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT "post_likes_user_id_fkey"
        FOREIGN KEY ("user_id") REFERENCES "profiles"("id")
        ON DELETE CASCADE ON UPDATE CASCADE
);
```

한 사용자가 같은 글에 두 행을 만들 수 없는 구조다. 댓글도 대상 ID만 다르고 같은 방식이다. 좋아요를 취소하면 해당 행을 삭제하므로, 눌렀다 취소하기를 반복한 횟수만큼 이력이 쌓이지 않는다.

외래 키에는 삭제 연쇄 처리를 붙였다. 글·댓글·프로필이 실제로 삭제되면 연결된 좋아요도 함께 정리된다. 다만 댓글의 숨김 처리처럼 행 자체를 지우지 않는 경우까지 외래 키가 해결해주지는 않으니, 그런 대상은 조회와 변경 로직에서 따로 제외했다.

새 테이블에도 기존 DB 규칙을 그대로 적용했다. RLS는 켜고 공개 정책은 만들지 않았다. 브라우저에서 테이블을 직접 조작하는 대신, 서버가 인증과 대상 조건을 확인한 뒤 Prisma로 접근하게 했다.

## 한 번 누른 결과를 지키기

### 같은 요청은 같은 뜻이어야 했다

화면에서는 좋아요를 한 번 더 누르면 취소된다. 그렇다고 서버 API까지 무조건 현재 값을 뒤집는 방식으로 만들지는 않았다. 같은 요청이 중복으로 들어왔을 때 등록하려던 좋아요가 취소되는 건 원한 결과가 아니었다.

| 요청 | 의미 | 반복해서 받았을 때 |
| --- | --- | --- |
| `PUT` | 좋아요가 있는 상태로 만든다 | 한 행만 남는다 |
| `DELETE` | 좋아요가 없는 상태로 만든다 | 없는 상태를 유지한다 |

클라이언트는 현재 선택을 보고 보낼 요청을 고른다. 서버는 그 요청이 뜻하는 최종 상태를 만든다. 등록에는 `createMany`의 `skipDuplicates`, 취소에는 `deleteMany`를 썼다.

글 좋아요를 실제로 쓰는 부분은 이 정도다. 이 코드는 대상 글을 확인하고 잠근 트랜잭션 안에서 실행된다.

```ts
if (liked) {
    await tx.postLike.createMany({
        data: [{ postId: post.id, userId }],
        skipDuplicates: true,
    });
} else {
    await tx.postLike.deleteMany({
        where: { postId: post.id, userId },
    });
}
```

없는 좋아요를 취소하는 것도 오류로 만들 필요가 없었다. 이미 원하는 상태이기 때문이다. 반대로 등록 요청이 겹쳐도 복합 기본 키가 중복 행을 막는다.

### 공개 여부는 잠근 뒤에 확인했다

중복 방지만으로 끝나지는 않았다. 좋아요를 눌러도 되는지 확인한 뒤 실제로 저장하기 전까지, 대상이 바뀔 수 있었다. 글이 초안으로 바뀌거나 댓글이 삭제되는 경우다.

글에 좋아요를 바꿀 때는 `SELECT ... FOR UPDATE`로 대상 글을 잠근 뒤 공개 여부와 작성자를 확인했다. 댓글은 댓글 행을 잠그고, 부모 글에는 `FOR SHARE`를 걸어 공개 상태를 확인했다. 확인과 저장을 하나의 트랜잭션 안에 뒀다.

**대상을 확인한 시점과 좋아요를 쓰는 시점을 따로 두지 않는 것**이 요점이었다. 같은 대상의 등록·취소 요청도 이 잠금에 맞춰 처리된다. 작업이 끝나면 집계한 개수와 내 선택 상태를 함께 돌려준다.

좋아요 개수를 올리려고 `post.update`를 호출하지 않은 것도 기존 규칙과 연결된다. 글의 `updatedAt`은 글을 고친 날이어야 했다. 누군가 하트를 눌렀다는 이유로 관리 화면의 수정일이 바뀌면 안 됐다.

그래서 글 자체에 카운터를 갱신하는 대신 좋아요 관계를 저장하고 그 개수를 읽었다. 이번 기능은 글의 내용이나 수정일을 바꾸지 않았다.

변경 API에는 로그인 확인과 요청 출처 확인, 사용자별 요청 제한도 붙였다. 다만 요청 제한은 기존 인메모리 방식이다. 서버리스 인스턴스마다 따로 세므로 서비스 전체를 통틀어 같은 상한이 보장된다고 보지는 않았다.

## 개수는 같고 선택은 다르다

### 내 하트를 공유 캐시에 넣지 않았다

좋아요 응답에는 성격이 다른 값이 섞인다. 총개수는 누구에게 보여줘도 되지만, 내가 눌렀는지는 로그인한 사람에 따라 달라진다. 내가 작성한 콘텐츠인지도 마찬가지다.

> *"숫자는 같이 봐도 되는데, 내가 눌렀다는 표시까지 같이 보면 안 된다."*

그래서 목록용 집계와 본문용 상태를 나눴다. 카드와 검색 결과는 공개 글의 개수만 조회한다. 본문에서는 글과 댓글의 개수에 `likedByMe`, `isMine`을 함께 받아온다.

| 데이터 | 쓰는 화면 | 처리 |
| --- | --- | --- |
| 공개 글별 좋아요 개수 | 카드·검색 결과 | 공통 집계 쿼리 공유 |
| 글·댓글의 개수와 내 선택 | 본문·댓글 | 사용자 ID를 포함한 쿼리 키 |
| 인증이 바뀌기 전의 내 선택 | 로그인·로그아웃 전환 | 기존 좋아요 쿼리 취소·제거 |

개인 상태가 든 API에는 `Cache-Control: private, no-store`를 붙였다. 브라우저에서 요청할 때도 `cache: "no-store"`를 지정했다. 성공 응답뿐 아니라 오류 응답에도 같은 캐시 헤더를 넣었다.

하지만 HTTP 캐시를 막는 것만으로는 부족했다. 화면에서는 React Query가 데이터를 들고 있기 때문이다. 쿼리 키를 `['likes', slug, userId]`로 만들어 글 주소가 같아도 사용자별로 구분했다.

로그인과 로그아웃 알림을 받으면 진행 중인 좋아요 조회를 취소하고 기존 쿼리를 지웠다. 이어서 현재 사용자 정보를 다시 확인하게 했다. 이전 계정의 선택이 새 계정 화면에 남는 것을 막기 위한 처리였다.

변경 요청이 늦게 끝나는 경우도 따로 봤다. 요청을 보낸 사람과 현재 사용자가 같은지 확인한 뒤에만 성공 결과나 실패 복구를 화면 캐시에 반영했다. 요청을 보냈다는 사실만으로 응답을 무조건 적용하지 않았다.

### 댓글 수만큼 API를 부르지 않았다

댓글마다 좋아요 버튼이 있으니 버튼마다 개별 조회를 붙이기 쉬웠다. 대신 글 본문과 댓글 버튼이 같은 쿼리를 쓰게 했다. 글 하나를 기준으로 글의 상태와 댓글별 상태를 묶어 받아온다.

서버에서도 댓글마다 내 선택을 다시 묻지 않았다. 댓글들의 개수를 가져오고, 내가 좋아요를 누른 댓글 ID를 모아 `Set`으로 만든 뒤 응답을 조립했다. 여러 조회가 들어가는 이 묶음에는 `RepeatableRead` 트랜잭션을 사용했다.

카드도 같은 집계 쿼리를 공유한다. 목록에 카드가 여러 개 있다고 해서 카드마다 서로 다른 API를 만들지는 않았다. 글 좋아요 변경이 성공하면 이 집계 캐시의 해당 글도 갱신하고 다시 조회하도록 했다.

다만 실시간 구독을 붙인 것은 아니다. 다른 독자의 반응이 모든 열린 화면에 즉시 방송되는 기능까지 만들지는 않았다. 이번에는 내 조작 뒤의 갱신과 화면에 다시 포커스가 왔을 때의 재조회로 범위를 정했다.

### 실패한 버튼만 되돌렸다

누른 뒤 서버 응답을 기다리는 동안 아무것도 바뀌지 않으면 반응이 둔해 보인다. 그래서 좋아요를 누르면 선택 상태와 숫자를 먼저 바꾸는 낙관적 갱신을 넣었다. 실패하면 이전 값으로 돌리고 오류를 알려준다.

문제는 글과 댓글이 하나의 캐시를 공유한다는 점이었다. 댓글 하나의 요청이 실패했다고 캐시 전체를 예전 상태로 돌리면, 그사이 바뀐 다른 댓글의 결과까지 지워버릴 수 있었다.

그래서 복구용으로 기억하는 값도 **이번에 누른 대상 한 건**으로 한정했다. 본문 버튼이면 글 상태만, 댓글 버튼이면 그 댓글 상태만 바꿨다. 같은 글에서 다른 변경이 진행 중이면 마지막 요청이 끝난 뒤 묶음을 다시 조회하도록 했다.

중복 클릭은 `ref` 잠금과 요청 중 상태로 막았다. 버튼에는 `aria-pressed`로 선택 여부를, `aria-busy`로 처리 중임을 표시했다. 색만 바뀌는 버튼으로 남기지 않으려 했다.

불러오는 중에는 숫자 대신 `—`를 보여줬다. 아직 모르는 개수를 0이라고 표시하면 실제로 반응이 없는 글과 구분이 안 된다. 조회가 실패했을 때는 다시 불러오는 동작도 따로 뒀다.

## 마지막에 남은 빈자리

### 로딩 화면도 기능의 일부였다

이번 배포 과정에서 실제로 놓친 것은 스켈레톤이었다. 관리 화면의 필터는 바뀌었는데 로딩 중 툴바는 이전 모양을 그리고 있었다. 화면이 다 뜬 뒤만 보면 잘됐는데, 뜨는 중에는 자리가 맞지 않았다.

로딩 중에도 시리즈 드롭다운이 보이도록 고치고, 댓글 검색창 스켈레톤에도 안내 문구를 맞췄다. 좋아요를 합칠 때는 댓글 스켈레톤에 좋아요 막대도 추가했다. 기능이 늘어난 만큼 기다리는 화면에도 그 자리가 필요했다.

> *"다 뜬 화면만 보고 끝났다고 하면, 뜨는 중인 화면은 누가 보나."*

모양 외에 스켈레톤의 범위도 문제였다. 댓글 관리 주소로 바로 들어가면 포스트 목록 스켈레톤이 먼저 나오고, 그다음 댓글 스켈레톤이 나왔다. 탭을 눌러 이동할 때만 봐서는 놓칠 수 있는 흐름이었다.

포스트 목록의 `loading.tsx`가 공통 관리 그룹에 있어서 댓글 경로까지 감싸고 있었다. 포스트의 `page.tsx`와 `loading.tsx`를 별도 `(posts)` 그룹으로 내렸다. 공통 헤더와 탭은 기존 레이아웃에 남기고, 포스트 로딩 화면의 범위만 좁혔다.

이 수정은 좋아요 저장 로직과는 별개였다. 그래도 같은 배포 과정에서 같이 드러난 문제라 여기 남긴다. 새 기능을 붙일 때 실제 화면뿐 아니라 로딩 화면과 직접 진입 경로도 함께 봐야 한다는 얘기다.

### 검사한 것과 아직 증명하지 않은 것을 나눴다

좋아요에는 별도의 회귀 검사 스크립트를 붙였다. 같은 사용자의 반복 등록·취소, 다른 사용자의 독립적인 반응, 본인 콘텐츠 거절, 초안·삭제·없는 대상 거절을 확인한다. 수정일이 바뀌지 않는지도 검사한다.

API 쪽에서는 로그인하지 않은 요청, 다른 출처에서 온 요청, 제한을 넘은 요청을 확인한다. 캐시 헤더와 마이그레이션의 RLS 설정도 검사 대상에 넣었다.

여기서 선을 하나 그었다. 이 검사는 **트랜잭션을 순서대로 실행하는 모의 DB 검사**다. 실제 PostgreSQL에 동시 요청을 던져 잠금 경합이나 교착 상황까지 검증한 것은 아니다. 스크립트 출력에도 그 한계를 적었다.

배포 과정에서는 lint와 타입 검사를 통과했고, 마이그레이션 적용 상태와 RLS를 확인했다. 배포된 화면의 좋아요 표시와 API 응답, 관리 목록의 집계도 확인했다. 마지막 등록·취소 동작은 직접 눌러 확인했다.

그렇다고 모든 화면 조건을 확인했다고 쓰지는 않겠다. 댓글 스켈레톤에 추가한 막대의 정확한 위치와 여러 폭에서의 배치까지 검증한 기록은 없다. 확인한 동작과 남은 화면 확인을 구분해두는 편이 맞았다.

## 결과

글과 댓글에 좋아요가 들어갔다. 카드와 검색 결과에서 개수를 볼 수 있고, 관리 화면에서도 집계를 확인할 수 있다. 본인 콘텐츠에는 숫자만 남고, 다른 사람의 공개 콘텐츠에는 등록과 취소가 가능한 버튼이 나온다.

| 항목 | 바뀐 뒤 |
| --- | --- |
| 가벼운 반응 | 글·댓글·답글에 좋아요 등록과 취소 |
| 중복 요청 | 사용자·대상별 한 행 유지 |
| 취소한 반응 | 별도 클릭 이력 없이 행 삭제 |
| 글 수정일 | 좋아요 변경으로 갱신하지 않음 |
| 개인 선택 상태 | 사용자별 캐시로 구분 |
| 낙관적 갱신 실패 | 누른 대상의 상태만 복구 |
| 로딩 화면 | 새 툴바와 좋아요 자리를 반영 |

새 테이블에서 좋아요는 0개로 시작한다. 기존 글이나 댓글을 옮겨 담는 백필은 필요하지 않았다. 화면에 표시되는 요소는 작지만, 그 작은 요소 때문에 데이터의 소유자와 갱신 범위를 다시 확인하게 됐다.

## 느낀점

- **작은 버튼도 상태의 주인은 분명해야 한다.** 총개수와 내 선택은 같은 응답에 들어 있어도 공유할 수 있는 범위가 달랐다. API 헤더와 화면 캐시를 함께 봐야 했다.
- **중복 요청을 막는 것과 같은 결과를 만드는 것은 다르다.** 화면의 연속 클릭을 막아도 서버에는 요청이 다시 올 수 있다. 등록과 취소의 뜻을 분리하고 DB 기본 키로 한 번 더 지켰다.
- **낙관적 갱신은 실패했을 때의 범위가 중요했다.** 먼저 숫자를 바꾸는 것보다 어디까지 되돌릴지 정하는 일이 더 조심스러웠다. 공유 캐시 전체를 복원하지 않고 대상 한 건만 복구했다.
- **로딩 화면도 현재 기능을 보여줘야 한다.** 완성된 화면만 고치면 기다리는 순간에 옛 UI가 남는다. 직접 주소로 들어가는 흐름까지 봐야 스켈레톤의 범위 문제도 드러났다.
- **검사 이름이 검증 범위를 넓혀주지는 않는다.** 모의 DB 회귀 검사가 통과했다고 실제 DB 동시성까지 확인한 건 아니다. 확인한 것만 적어야 다음에 더 봐야 할 부분이 남는다.

좋아요를 붙이고 나니 하트보다 그 뒤의 상태를 더 오래 설명하게 됐다. 그래도 독자에게 보이는 건 가볍게 누를 수 있는 작은 버튼이면 충분하다. 그 단순한 동작이 앞뒤 화면에서 같은 뜻을 유지하도록 정리한 작업이었다.
