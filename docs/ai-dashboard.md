# AI 활용 페이지 운영

`/ai`는 공개 소개·주별 집계·관련 글이고 `/ai/manage`는 관리자용 분석 화면이다. 통계 계산의 원본은 dev-bootstrap `skills/usage-report/scripts/usage_store.py`이며, `usage_publish.py`가 블로그용 집계만 전송한다. 기존 승인된 HTML 보고서도 같은 집계를 사용한다.

## 연결 순서

1. 먼저 `ai` slug인 기존 포스트가 없는지 조회한다. 있으면 임의 변경하지 않고 URL 이관을 결정한 뒤 진행한다.
2. 대상 DB 백업과 적용 대상을 확인하고 `yarn prisma migrate deploy`로 새 집계·콘텐츠 테이블을 만든다. RLS는 활성화하며 익명/일반 사용자 정책을 추가하지 않는다.
3. 블로그 서버 환경에 32자 이상의 무작위 `AI_USAGE_INGEST_KEY`를 설정한다. `NEXT_PUBLIC_`을 붙이지 않는다. 같은 값을 private KB 저장소 Actions secret에 설정한다. 블로그 코드를 배포한다.
4. private KB 저장소의 Actions variables에 `AI_USAGE_INGEST_URL=https://<블로그>/api/internal/ai-usage`, `AI_USAGE_EXPORTER_REF=<내보내기 코드가 포함된 dev-bootstrap의 전체 커밋 SHA>`를 설정한다. exporter 저장소는 public이고 집계 자료는 private KB에만 있다.
5. KB 기본 브랜치의 `publish-ai-usage.yml`을 수동 실행해 실제 집계·공개 응답·관리자 화면을 확인한다. 예약은 10:17 KST 하루 1회다. 매번 코드 배포나 AI 호출을 하지 않는다.

예약 작업은 기본 브랜치에 workflow가 있어야 실행된다. 실행 지연·실패 시 기존 정상 스냅샷이 남고 48시간 이후 갱신 지연을 표시한다. 실패 원인은 private 저장소의 Actions에서 확인한다. 이미 업로드된 기기 자료만 집계하므로 PC가 꺼진 동안 새 로그는 수집되지 않는다.

## 데이터·게시 기준

- DB는 연도별 최신 스냅샷만 저장한다. 원본 이력은 private `usage-data` 브랜치가 유지한다. 새해에도 지난 연도 자료를 삭제하지 않는다.
- 공개 데이터는 서버의 명시적 필드 목록으로 투영한다. 프로젝트·모델·추론·작업·기기 식별자와 내부 개선 참고 자료는 공개 응답에 넣지 않는다. 원문 대화·명령·로그·세션 키는 내보내지 않는다.
- 공개 화면은 Codex·Claude의 주별 사용량을 동일 눈금의 막대로 비교한다. 도구 간 비중 퍼센트 대신 실제 수치를 표시하며 전체 토큰·캐시 제외 입력·출력을 전환한다.
- 전체 토큰은 입력+출력이며 캐시는 입력에 포함된다. 캐시 관측이 부족하면 비율을 미상으로 표시한다. 미관측 주는 0과 구분하고 완료되지 않은 주·부분 관측을 표시한다.
- 작업 시각과 세션 연결이 없으면 날짜 미상 작업은 별도 기록이며 연결 토큰은 '연결 없음'이다. 기간별 작업 성공률·효율 점수를 추정하지 않는다.
- 공개 상단 소개는 `DEFAULT_AI_INTRO`의 기본 문구를 사용한다. 소개 편집 UI·저장 API·DB 조회는 제거했다. 기존 `ai_publications` 테이블과 데이터는 보존하지만 사용하지 않는다.
- 관리자 탭은 사용량·작업 기록·수집 상태다. 작업 기록은 한 표에서 한 일·프로젝트·확인 결과·날짜·상태를 먼저 보여 주며, 검사와 남은 일·참고 지식·원본은 행 상세에 둔다. 날짜가 있는 작업만 KST 기간·정렬에 적용하고 날짜 미상도 같은 표의 날짜 값으로 구분한다. 주별 진단과 기기 상태는 `수집 상태` 탭에 둔다. 사용량 표 아래 서랍으로 두면 펼칠 때 표가 줄어 둘 다 보기 어려웠다(사용자 판단, 2026-10-02). 수집 상태 탭은 연도·기간·정렬만 따르고 검색창을 두지 않는다.
- task의 선택 `presentation`은 한국어 제목·요약·작업 시각, 설명된 검사(`checks`), 남은 일(`followUps`), 참고·적용 지식(`knowledge`), 근거(`evidence`)를 담는다. 기존 원본 검사와 식별자는 유지하며, 보완이 없는 기록도 열어볼 수 있다. 검사 실패와 현재 미해결 오류, 문서 참조와 실제 적용을 구분한다.
- 과거 기록 보완은 private usage-data의 `task-presentations/<project+id digest>.json`에서 원본과 결합한다. 파일 형식은 `{project,id,presentation}`이며 작업별 근거를 포함한다. 개인 기록을 이 public 저장소에 넣지 않는다. 새 수신부 배포 후 exporter의 고정 SHA와 보완 자료 동기화를 함께 반영해야 운영 관리자 화면에도 새 설명이 도착한다.
- 하단 관련 글은 따로 쓰지 않는다. `AI_POST_SERIES`에 속한 발행 글을 글 상세와 같은 `CarouselSlider`로 최신 5편까지 보여 주며, 글을 발행·수정하면 `revalidatePost`가 `ai-public` 캐시를 비운다. 시리즈를 추가하려면 그 상수만 고친다.
- 개선 기록 편집은 없앴다. 예전 `ai_publications`의 improvement 행은 지우지 않았지만 화면·API 어디에서도 읽지 않는다.

## 전송 계약과 실패 처리

`POST /api/internal/ai-usage`: 전용 Bearer key, schema 1 / metrics `usage-v1`, 전체 source SHA, GitHub workflow의 증가하는 `run_number`, 생성 시각, 연도별 집계, 내부 개선 참고 자료. 8 MiB 제한. 공개 조회는 별도 데이터 투영만 사용한다.

인증·형식·합계 검증 후 트랜잭션으로 교체한다. 같은 순번의 재시도와 낮은 순번은 성공 응답의 `accepted:false`로 무시한다. workflow를 삭제·재생성하거나 이름을 바꿔 순번이 초기화되면 이전 최대값보다 큰 순번으로 복구하는 이관이 필요하다. 수집기/지표 버전 불일치와 원본 무결성 실패는 게시하지 않는다. 서버 오류·전송 실패는 Actions 실패로 남으며 수동 재실행한다.

키는 서버와 Actions에서 함께 교체한다. 원격 실행 로그·공개 저장소에 집계 payload나 키를 출력하지 않는다. 관리자 API는 `profiles.role` 기반 기존 인증을 사용한다.

## 검증

- `yarn verify:ai`: 공개 필드 분리·토큰 합계·기간·스키마·예약 slug 검사.
- `yarn verify:ai-api`: 격리 로컬 DB와 서버 전용 통합 검사. `AI_TEST_URL`, `AI_TEST_KEY`, `AI_TEST_PAYLOAD` 필요. 운영 호스트에서는 실행을 거부한다. 격리 인증 fixture의 `AI_TEST_ADMIN_COOKIE`, `AI_TEST_USER_COOKIE`, `AI_TEST_POST_ID`(`ai-test-` 접두사)를 함께 지정하면 역할 검사와 제거된 소개 API·관련 글 재발행 검사도 실행한다. 생략하면 해당 검사는 건너뛰었다고 표시한다.
- `yarn verify:analytics`, `yarn lint`, `yarn tsc --noEmit`, `yarn build`: 기존 화면 영향과 배포 검사.
- 실제 로그인·기본 소개·관련 글 비공개 전환과 모바일/데스크톱, 라이트/다크 테마, 내부 스크롤·빈 결과·로딩·실패 상태를 확인한다.

### 2026-09-30 로컬 검증 결과

스키마·공개 필드·기간 검사, exporter 7개·기존 tracker 28개, 기존 통계 회귀와 마크다운 12개, lint·타입 검사·표준 환경 production build가 통과했다. 실제 자료의 주요 합계 6개가 기존 집계와 일치했고 HTML 승인 지문도 유지됐다. 운영 DB에서 `ai` slug 충돌은 0건이었다(조회만 수행).

PGlite 격리 DB와 로컬 서명 인증 서버로 HTTP 수집·중복·순서 역전·익명/일반 사용자 인가, 관리자 게시·비공개 전환을 확인했다. 관련 글의 비공개 전환·재발행은 다음 공개 요청에 즉시 반영됐으며 통합 회귀 검사에 포함했다. 일반 사용자 `user_metadata`의 ADMIN 값은 권한으로 인정되지 않았다. 새 두 테이블의 RLS 익명 직접 조회도 차단됐다. 실제 운영 Supabase 로그인·운영 이관·원격 예약 실행은 아직 실행하지 않았다.

Orca는 탭 생성 뒤 runtime 연결이 종료돼 Playwright로 대체했다. 실제 관리자 경로에서 1440/390px 폭 모두 문서 scrollTop=0, 표 scrollTop=400, 컨트롤 위치 유지와 가로 넘침 없음을 확인했고, 게시/비공개 버튼을 실제 API에 연결해 검증했다. 공개 화면의 기간 필터·모바일·두 테마와 관리자 미리보기도 확인했다. 초기 임시 UI 경로는 제거했다.


정확한 수행 시각이 없는 과거 기록은 내부 ID에 유일한 유효 날짜가 있으면 ‘기록명 기준’ 날짜를 표시합니다. 이는 확인된 수행일이 아니므로 기간 집계·수행일 정렬에서 제외하며 원본 시각을 만들지 않습니다. 여러 날짜나 잘못된 날짜는 채택하지 않습니다.

작업 목록은 제목·한 줄 요약·검사 상태·날짜·작업 상태로 압축하고 긴 검사명과 설명은 펼친 상세에서 제공합니다. 실패/미확인 검사가 있으면 통과보다 우선 표시합니다. 프로젝트별 반복 표 머리글은 콘텐츠와 함께 스크롤하며 고정하지 않습니다.


필터 바는 블로그 관리 목록과 같은 한 줄(기간·보기 방식, 검색, 필터, 정렬)이며 640px 이하에서만 기간 줄을 나눕니다. 프로젝트 다중 선택은 블로그의 태그·시리즈처럼 필터 창 안에 두고 고른 값은 칩으로 보여 줍니다(사용자 요청, 2026-10-02 — 10-01의 "필터 밖 상시 드롭다운" 결정을 대체). 관리 표의 양 끝 칸 안쪽 여백은 같은 1rem 이고, 스크롤바는 오른쪽에 따로 비운 10px 자리에서 움직여 마지막 칸 글자에 붙지 않는다. 내용 검색은 작업 제목·요약·검사·후속 작업·연결 지식에 적용하며 프로젝트는 전용 선택으로 거릅니다. 사용량 탭의 내용 검색은 도구·모델·추론 수준을 검색합니다.



작업 기록은 프로젝트 그룹 없이 단일 표를 사용합니다. 프로젝트는 열과 상시 필터로 구분하며 개별 행만 펼칩니다. 확인된 수행일 순으로 정렬하고 수행일 미확인 기록은 같은 표 아래에 표시합니다. 

### 상세 작업과 프로젝트 간 인계

선택 `task.activity`는 MuRing-KB 계약의 목적·역할·결과·근거·날짜 정밀도 및 선택 `handoffs`를 수신한다. 구조와 의미 검증은 `src/lib/ai-activity.ts`, 공유 가상 fixture 41개는 `scripts/fixtures/ai-task-activity.json`에 있으며 `yarn verify:ai`에서 대조한다. 날짜만 확인되면 원래 달력 날짜로 기간을 판단하고 자정 시각을 만들지 않는다. activity의 명시적 날짜 미상을 legacy 날짜로 덮지 않는다. 날짜만 보완된 activity도 기존 presentation 검사·설명을 보존한다.

관리자 행 상세에서 발신·수신 프로젝트, 요청, 입력 수락·수신·착수·보류·결과와 근거를 확인한다. 서로 다른 activity의 근거 ID는 해당 원문을 찾아 비교하며 같은 인계/이벤트의 중복만 합친다. 헤더·이벤트·종료 결과 충돌은 원문 변형을 모두 보존하고 상태를 확정하지 않는다. 날짜만 있거나 시각 미상인 이벤트는 정확한 발생 순서를 단정하지 않는다. `dispatch_accepted`는 상대 수신이 아니다.

연결 작업은 같은 인계 ID가 있는 명시적 기록 또는 정확한 프로젝트+작업 ID로만 연다. 연결 대상이 미상이거나 충돌하면 임의 작업을 고르지 않는다. 현재 필터를 바꾸지 않고 연결 작업 상세를 표시한다. activity와 인계는 private 전용이며 기존 공개 projection은 확장하지 않는다. 계약 지원과 운영 전송 활성화는 별개다.

작업 기록 표는 포스트 관리 표와 `styles/list-table.ts`의 기본 스타일을 공유한다. 제목은 행에서 한 번만 보여주고, 요약은 접힌 행 또는 펼친 상세 중 한 곳에서만 표시한다.

설명이 보완되지 않은 작업은 제목 자리에 작업 ID를 날짜 조각을 뺀 띄어쓰기 형태로 보여 준다(모두 같은 문구로 보이면 구분할 수 없다). 상세에는 빈 절을 늘어놓지 않고 수집된 원본 검사 결과만 보여 준다. 효율 비교 보류·날짜 기준 안내는 결과 줄 옆 정보 아이콘에 둔다.

### KB 검색·선택·적용 판단

선택 `activity.knowledgeDecisions`(MuRing-KB 계약 2026-10-02 "KB 검색→선택→적용 판단→검증 연결")를 수신한다. 누락은 수집 안 됨, `null`은 미상, `[]`는 확인한 판단 대상 없음이다. 구조는 `ai-activity.ts`, 의미 판정은 MuRing-KB `scripts/kb_knowledge.py`의 `validate_decisions`와 같다(정규 KB 상대 경로, id·문서 유일, 검색 선택은 searchRefs 필수·직접 선택은 빈 배열, 미상 외 판단은 근거 필수, 적용은 적용한 곳과 통과/실패 검증 근거 필수, 예전 knowledge 의 적용/참고와 모순 거부). 공유 fixture는 53개다.

관리자 작업 상세에 문서별로 찾은 경로(검색/직접), 판단, 이유, 적용한 곳 또는 쓰려던 곳, 검증을 보여 준다. 실제 KB 적용 이력(usage 기록)은 이 자료에 실려 오지 않으므로 화면은 대조 결과를 만들지 않는다. 적용 판단에는 KB `knowledge-review`로 대조한다고 표시하고, 적용하지 않은 판단은 이력 대상이 아니라고 구분한다. 판단 기록 없이 예전 knowledge 에만 적용으로 남은 문서는 따로 알린다. 공개 투영은 바꾸지 않는다.

작업 상세는 행 제목과 다른 한 줄 요약 → 이름·값 줄(한 일·AI 역할·사람의 판단·결과·검증·남은 일·지식·KB 판단·인계) → 맨 끝 `원본 기록과 근거` 하나로 구성한다. 검사는 배지+이름 한 줄이고 방법·한계는 이름과 다를 때만 작게 붙인다. 인계 이벤트는 한 줄 머리(무엇·언제·누가)+요약이며 근거는 인계마다 한 번만 접는다. 작업 근거·원본 검사·설명 보완 근거는 모두 `원본 기록과 근거`에 모은다. 값이 없는 줄(인계 없음 등)은 두지 않아 같은 안내가 기록마다 반복되지 않게 한다. 좁은 화면은 이름이 값 위에 작게 붙는 한 열이다. 상세는 행 아래 한 톤 다른 면(`--recordbackground`)에 두고 이름·값 줄은 가는 선으로 나누며, 인계 이벤트는 점과 세로선의 타임라인이다. 연결 작업 링크는 포트폴리오와 같은 공용 링크 모양(`styles/link.module.css`)을 쓴다. 인계 링크는 상대 작업이 지금 표에 있으면 그 행을 펼치고 작업 기록 상자 안에서만 스크롤해 잠깐 강조하며, 조건에 걸러져 없을 때만 표 위 칸에 띄운다. 강조는 스크롤이 도착한 뒤에 켜져 잠깐 머물다 서서히 사라진다. 행 제목 아래 한 줄은 보완 설명 요약 → 첫 결과 → "한글 설명 보완 전 기록" 순으로 채워 모든 행이 같은 구조다. 상세 맨 위에는 늘 그 요약 전체를 쓰고, 펼친 동안 행의 한 줄 요약 자리까지 제목이 쓰며, 짧은 제목은 세로 가운데로 내려오고 긴 제목은 두 줄까지 펼쳐진다. 이 변화는 FLIP 애니메이션(220ms)으로 잇는다(행 높이 불변, 같은 문장 한 번만 보임). 요약이 첫 결과에서 왔으면 `결과` 줄에서 그 문장을 뺀다(사용자 선택 A, 2026-10-02). 상세는 높이 0에서 펼쳐지고 닫힐 때 접힌다. `원본 기록과 근거`의 작업 근거는 activity 의 어느 항목(작업일·결과·검증·인계·KB 판단 등)을 뒷받침하는지 함께 적고, 작업일에만 쓰인 근거는 작업일 줄의 쉬운 설명으로 대신한다(원문 메모는 title). presentation.evidence 는 `설명 출처`다.
